FPSci Harness Rewrite

Rebuilding everything around the aim-training binary: one database per run, a submit gate the player controls, and CSVs sorted by scenario and person. The four scenarios themselves do not change.

Updated 21 Aug 2026 Stock FPSci v23.04.01 Scope: harness only Next: play a sitting with the strap on

§ 0Decisions locked

Scope Harness only Keep FirstPersonScience.exe and the scenario definitions exactly as they are. Rewrite the config, the launcher, the exporter and the layout around it.
CSV layout Scenario → person → grain A directory per scenario, a directory per person inside it, one file per grain so no file mixes two row types.
Export trigger Player submits the run A Yes/No prompt at the end of every run. Yes exports it; No keeps the raw recording but leaves it out of the analysis tables.
Warm-up condition Re-selectable dropdown Set in the launcher before playing, changeable at any point between runs — the same feel as the scenario dropdown, not a one-shot prompt.

Everything below follows from those four. Where a decision has a consequence you might not want, it is called out rather than buried.

§ 1Why the saving feels wrong

The post-game behaviour is not a collection of small quirks. It is one config line, and roughly a dozen workarounds built on top of it.

One line disables the entire end-of-session path

sessionFeedbackDuration: 86400.0 keeps scenarios from vanishing off the menu, but it does that by making the completion block at Session.cpp:696–745 unreachable. That block is where FPSci does all of its end-of-session work:

What is deadWhereConsequence you are living with
endLogging()Session.cpp:720Nothing is flushed when a run ends. Data becomes durable only when the next session replaces the Session object, or on a clean quit.
commandsOnSessionEndSession.cpp:733Unusable — which forced the CSV parse onto commandsOnSessionStart, so it always parses the previous run.
markSessCompleteSession.cpp:724Sessions.complete is always 0. No run is ever recorded as finished.
Session-level questionsSession.cpp:697Forced the warm-up prompt down to a task question, asked after the run instead of before it.
saveUserConfig(true)Session.cpp:729Sensitivity and user state are not persisted at the natural moment.

Every batch file in FPSci-bin/ exists to paper over one of those five rows. play.bat waits for the process to exit because nothing flushes on its own. userstatus.sessions.csv is emptied and marked read-only because markSessComplete was the thing hiding scenarios. parse_results.bat carries a lock file and a stale-lock sweeper because it runs at the wrong end of the run.

The unlock

UserStatusTable has an allowRepeat flag, default false (UserStatus.h:23). With it on, GuiElements.cpp:668–675 removes a completed session from the dropdown one entry at a time instead of removing every match. List gridshot fifty times in a participant's session array and it stays on the menu for fifty plays.

That is FPSci's own mechanism for repeated sessions. Turning it on lets sessionFeedbackDuration go back to a couple of seconds, which brings all five dead rows back to life and makes the entire workaround stack unnecessary.

Nothing is durable until you leave

Trial rows, question answers and target metadata sit in the same 1 MB queue as per-frame data (Logger.h:40–56). At the measured data rate that queue fills roughly every fifteen seconds. Alt-F4, a crash, or killing the process from Task Manager loses the run you just played — not merely its tail, because the Trials row and the warm-up answer are queued alongside everything else.

The parse does not scale, and runs at the wrong moment

Measured on the current pilot data: 13.5 seconds to copy 72 MB of databases to %TEMP% and re-derive every metric from scratch. It is O(all data ever recorded) and it fires when you start a scenario — so it runs concurrently with the opening seconds of your next run. At roughly 7–12 MB per sixty-second run, a twenty-participant study is a few gigabytes and a multi-minute parse on every single scenario selection.

Per-shot error metrics are unaffected; per-kill eccentricity for gridshot and microadjust simply is not available from the stock binary.

§ 2The new shape

2.1  Sessions complete normally again

Now
  • sessionFeedbackDuration: 86400
  • Run ends on a dead-end screen you leave with Esc
  • Warm-up dropdown fires after the run, as a task question
  • Parse fires when the next run starts
  • Two launch paths with different data guarantees
Next
  • sessionFeedbackDuration: 2.0 plus allowRepeat: true
  • Score screen, then a Yes/No submit prompt, then the menu
  • Warm-up is already known — set in the launcher before play
  • Export happens after the run it belongs to
  • One launch path: run_study.py

2.2  One database per run

Setting logToSingleDb: false makes FPSci name each results file <scenario>_<user>_<UTC timestamp>.db. That single change buys four things at once:

  • The filename already encodes scenario, person and time — the exact keys the new folder layout needs.
  • Export becomes incremental. One finished run is one small file, parsed in well under a second, instead of a full rescan.
  • A crash can damage at most one run.
  • correlate.py's "newest database" becomes precisely "the run you just played", rather than a shared file containing every run you have ever done.

The cost is that the config hash leaves the filename, so provenance moves into the Experiments table — which is exactly why the apostrophe fix in §1 stops being cosmetic. With it repaired, every run's database carries the full config text and its hash. Confirmed on the Phase 1 runs: 30,139 bytes of config, hash 0x404f74c6.

Discovered in Phase 1

A database is opened the moment a scenario is selected, not when a run starts. Browsing the menu therefore leaves stub files behind — the two verification runs produced six databases, four of them stubs of 0.1–0.5 MB. Under the old single-database setup these were the harmless zero-trial rows in Sessions; now they are files.

Classification has to be on gameplay, not on the Trials count alone, because those two cases are different: a stub has zero trialTask frames, while a run abandoned mid-trial has thousands and no Trials row. The first is disposable, the second is real data that needs looking at. The exporter sorts them; stubs go to results/_stubs/ rather than being deleted, since raw data is never destroyed.

2.4  The submit gate

A session-level question, which becomes reachable again the moment §2.1 lands:

"questions": [
    {
        "type": "MultipleChoice",
        "prompt": "Submit this run?",
        "title": "Submit",
        "options": [ "Yes", "No" ],
        "optionKeys": [ "y", "n" ],
        "randomOrder": false
    }
]
Watch this one

randomOrder defaults to true for MultipleChoice questions (FpsConfig.cpp:703–707). Without setting it false, Yes and No swap places between runs — a genuinely dangerous default for a submit button. optionKeys also lets the answer be given with Y or N, so the player never has to find the mouse.

The exporter reads the answer from the Questions table and routes accordingly: Yes into the person's tables, No into _discarded/, no answer at all into _pending/. Because presentQuestions gates session completion, an unanswered prompt also means the session never completes — so an abandoned run correctly stays on the menu to be replayed.

Discovered in Phase 1

Questions.response stores the option label as displayed, so with optionKeys set it reads "Yes (Y)", not "Yes". Do not match on it directly. The row also carries presented_responses and response_array, so the clean answer is recovered by finding the response in the first and taking the same index from the second — which stays correct even if options are ever shown in random order.

This single field decides whether a run reaches the analysis tables, so the exporter must treat anything it cannot map as unanswered and route to _pending/ rather than guessing.

One consequence to decide on: answering No still consumes one slot from the repeat quota. The simple answer is to set the quota generously (50 per scenario) so it never binds, and treat userstatus.sessions.csv as a progress log rather than a limit.

2.5  The warm-up dropdown

The launcher holds a small always-available control panel with the participant and the warm-up condition. The condition is a dropdown, changeable at any time between runs, and every run is stamped with whatever is selected when that run starts. It is written into _index/sittings.csv the instant a new database appears, so it can never be lost to a crash and never has to be re-answered per run.

Trade-off

The dropdown lives in the launcher window, not next to the scenario dropdown inside the game. FPSci has no configuration hook for adding a menu control, so an in-game version would require building a patched binary — the option you set aside. In practice this means alt-tabbing when you want to change condition, which is an experimenter action between sittings rather than something the player does. If it turns out to grate, adding a real in-game dropdown is a contained C++ change we can revisit.

2.6  What does not get rewritten

Two things are already right and should survive intact. The scenario definitions — targets, eccentricities, timings, weapons — carry over unchanged; only the logging and session-lifecycle keys around them move.

The metrics engine in fpsci_parse.py is the most valuable code in the project: correct spherical geometry, a fixed 10 ms velocity window that survives a 470 Hz frame rate, per-frame angular radius from true camera distance, submovement detection. Rewriting it would be throwing away the hard part. It gets refactored from a CLI script into an importable module with its behaviour pinned by a test, and the new exporter calls into it.

Phase 2~2–3 hDone

Metrics engine becomes a module

app/fpsci_metrics/ is now an importable package of eight modules — config, geometry, results, sessions, trial, aggregate, questions, csvio. analyse("FPSci-bin/results") returns a MetricSet of runs, trials, shots, targets and sessions, and writes nothing: where rows go is the exporter's decision, not the engine's.

analyse_trial and the aggregation functions were extracted verbatim from the original by script rather than retyped, and the extraction was itself verified line-by-line against the source range. Only imports moved. fpsci_parse.py stays untouched as the reference implementation.

The decode helper written during Phase 1 verification moved into questions.py, so check_phase1.py and the future exporter share one implementation of the rule that Questions.response is a displayed label rather than an option.

Verified python app/tests/test_golden.py — all 5 tables byte-identical over 6 databases (2 runs, 26 trials, 181 shots). Byte-for-byte rather than value-by-value, so it catches a moved column or a differently-formatted float, not just a changed number.
Phase 3~2–3 hDone

The exporter

app/export.py. One database in, per-scenario and per-person rows out: it classifies run vs stub vs abandoned, decodes the submit answer, joins the sitting manifest for the warm-up label, slugifies the person through the registry, merges into the four grain files and updates _index/. --rebuild, --sweep-stubs and --dry-run are there.

Run numbers come from _index/runs.csv, not from the metric engine. The engine numbers sessions across whatever databases it was handed, which is only right when it is handed all of them — without this, exporting one new run would renumber it as that person's first.

Files are merged rather than appended: a re-export replaces a run's rows instead of duplicating them, a run introducing a new column cannot corrupt the file, and output is sorted so a rebuild is reproducible. At a few tens of thousands of rows, rewriting is cheaper than the bookkeeping needed to avoid it.

Verified test_export.py: 16 checks over all three routing paths, including a missing and a garbled submit answer — both correctly become _pending/ rather than being guessed. Separately confirmed on the real tree: re-running changes nothing, --rebuild twice is byte-identical, and an incremental export produces the same tree as a full rebuild.
Phase 4~3–4 hBuilt

The launcher

python app/run_study.py. A Tk control panel with the participant and the warm-up dropdown, a preflight gate, config generation, process launch, and a watcher that exports each run seconds after it finishes with a final sweep when the game closes.

The warm-up dropdown stays live for the whole sitting. Changing it closes the open stretch in _index/sittings.csv and opens a new one, so each run is attributed by when it was played rather than by anything the player has to remember. The exporter already joined on those windows, tested since Phase 3.

Preflight replaced config templating. The plan had the launcher render experimentconfig.Any from a version-controlled master, which would have silently reverted any hand edit. It instead regenerates only the two participant-dependent files and checks the experiment config — seven checks, one per thing that actually went wrong during this rewrite. A problem blocks the launch and says why. Catching a regression is worth more than owning the file.

Phase 5~1 hDone

Retire the old path

The batch files and the old analysis/ tree went in Phase 1, so this was documentation — except it was not. Chasing the doc updates surfaced a functional break on the sensor side.

One sitting is now several databases, and correlate.py only read one. It picked the newest .db, which under per-run databases means a four-scenario sitting would have been joined against its last run alone — silently, with a plausible-looking result. It now selects every database whose gameplay falls inside the recording window and merges them; a menu stub has no trial span and drops out without a special case. --fpsci-db still pins it explicitly and is now repeatable.

The metric engine was opening raw databases read-write. Inherited verbatim from the original parser, which got away with it by working on copies. export.py and correlate.py both open read-only and say why; the engine now does too. Phase 6~2 hDone

Fold the heart-rate join in

correlate.py counted shots and computed accuracy itself while the exporter computed it from the metric engine. Two implementations of one quantity is how a thesis ends up with two different accuracies for the same trial. It now imports app/fpsci_metrics and derives every aim number through it, attaching physiology over the same window. count_events and subject_for are gone.

The join got richer rather than thinner. trials_hr.csv now carries reaction time, angular error, time on target, path efficiency, submovements and peak velocity beside HR and RMSSD, and sessions_hr.csv became one row per run — the analysis unit — carrying the warm-up condition, the aim metrics and the physiology together. Run-level rates come from the engine, which recomputes them from run totals rather than averaging across trials, so flicks with its 25 short pair-trials is not skewed.

The warm-up label is joined from the launcher manifest through export.warmup_for — the same function the exporter uses, not a second copy of the rule.

Verified sensors/tests/test_shared_metrics.py runs both consumers over the same databases and diffs every shared column: 8 metrics across 6 trials plus the run rollup, all exact. Trial accuracy now has exactly one implementation, at fpsci_metrics/trial.py:166. Seven suites green across both halves.

§ 6What stays broken, and open questions

Accepted, because scope is harness-only

  • The durability window. Data is still queued in-process until 1 MB accumulates. Per-run databases shrink the blast radius to a single run, and the exporter can flag any database with no Trials row, but a hard kill still loses that run. Quitting through the menu remains the rule.
  • A race in the logger. addToQueue reads the queue sizes outside the mutex it just released (Logger.h:70–82), so the size check races the writer thread. Upstream bug, no observed impact, unfixable without building.
  • Per-kill data in respawning scenarios. As in §1 — one Targets row per entity, not per respawn.
  • The warm-up dropdown is not in-game. See §2.5.

Needs your call, but not blocking

  • How many runs per scenario per participant does the protocol actually need? If it is a fixed number, the repeat quota should be that number rather than 50, and the menu emptying becomes a useful "you are done" signal.
  • Should raw data move to a shared root? The sensors side already uses data/raw and data/processed. Putting FPSci databases under the same convention would unify the two halves, at the cost of a path change in every script. Easy now, annoying later.
  • Should the exporter re-check _pending/? A run with no submit answer might deserve a prompt in the launcher next time it starts, rather than sitting unnoticed.
